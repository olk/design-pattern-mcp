## 2. Where the wall-clock goes

Measured on the live dev stack (2026-09-25, memory + repo-recorded):

- **End-to-end**: `make client-async` trio = **1162 s** for a full DesignResult (8 decision parts → exactly 8 cross-encoder requests of 35-51 s each, Σ≈333 s retrieval).
- **Rerank**: 51.3 s per 48-doc batch, 9.9 s for 8 docs (CPU TEI sidecar; config.py:109-111). Lossless recall (caps 0/0) = 10 chunks ≈ **9.8 min per decision part** — hence shipped caps dense_top_k/bm25_top_k = 20/20 keeping the fused pool ≤40 ≤ max_batch_size 48 (invariant documented in docker-compose.yml:75-79).
- **Query embedding**: 13-29 s per call on the CPU TEI embed sidecar (config.py:94-97).
- **Sequential provider calls per request** (defaults): 6 pipeline LLM calls + **19-21 reasoning-layer calls** (4 analyze + 3 weights + 3 generate ×2 attempts + 3 evaluate ×2 attempts [+2 retry when reselection fires]) ≈ **25-27 strictly sequential LLM round trips**, plus one Node MCP subprocess spawn + stdio handshake per reasoning step (keep_alive=False, `src/reasoning/client.py:471-487`), each step bounded 20 s. Nothing in the hot path runs concurrently.
- Known dead cost: `_reasoning_block("retry")` at pipeline.py:1625 awaits a 2-step trace **whose result is discarded** — 2 LLM calls + 2 subprocess spawns bought for nothing.

So latency = (reasoning layer: 19-21 LLM calls + spawns) + (retrieval: 8 × [embed 13-29 s + rerank 35-51 s]) + (4-6 generative LLM calls) + (deterministic arithmetic, negligible).

**Deployment-tier caveat**: every number in this section is a **CPU-tier measurement** — the shipped stack runs both TEI sidecars on CPU images, and the server deploys on arbitrary hosts. On a modern-GPU host (CC ≥ 7.5) the existing `make docker-up-gpu` path moves the embed sidecar (and a matching CUDA rerank image, same recipe) onto TEI CUDA and the 35-51 s/part rerank collapses; retrieval stops being dominant there. §4/§5 verdicts are tier-qualified accordingly.

## 3. What Jev is (and is not)

Jev is a hosted "System One" decision model: one HTTPS round trip (`POST /v1/systemone`, Bearer key, `model` pinned — use `jev-1.13.0`, not `jev-latest`, when thresholds matter), you send a `state` (string/JSON/array) plus a map of typed `questions`; all questions are evaluated in parallel in **one round trip, claimed 70-500 ms**. Output tokens are free; input is billed ~$0.25-0.42/M tokens. Context: ~64k tokens combined on TypeSafe direct (32k via OpenRouter). Rate limits (1200 req/min, 250k tok/s) are far above this server's volume.

Three primitives (docs.typesafe.ai, learnjev.com):

- **choice** — one of ≤255 labelled options; returns winning key + per-option probabilities + confidence.
- **score** — position on a 2-10 level ordered scale you describe; returns fractional score + full distribution + confidence. Ordered, not metric: threshold on it, never do arithmetic between levels.
- **noul** — calibrated p(yes) ∈ [0,1]; no confidence field; the probability is the signal.

Vendor-documented traps that matter here: **noul 0.5 means ignorance, not "middle"**; a noul and a logically-similar choice **can disagree** — never share thresholds across primitives or assume complementary sums; above ~200 options choice slows (two-stage scoring); confidence floors should scale with risk (0.5 = genuinely unsure → escalate; higher bars for consequential actions).

What Jev cannot do: generate prose. It cannot write the A+B brief/part descriptions, the G generation content, or the H evaluation findings — this pipeline's contracts (docs/result-schema.json) require that prose. It also cannot be the final selection authority: §15 determinism, the veto/CSP/MAUT/fallback contracts, and the repo's verification program (mutation ratchet + FizzBee models over the deterministic modules) all assume selection is arithmetic. Jev's lane, per its own use-cases page (routing, scoring/prioritizing, gating, model routing, context compaction), is exactly: **small, typed, high-volume judgments your code branches on.**

Data-governance framing (tier-independent): hosted TypeSafe sends requirement text off-machine (default-off config, §7); the Kev/Von/Rizzo-Flow local-server path keeps everything on-box at some quality cost; the Laya/Von/NanoJev fine-tune path additionally removes the API bill but adds a training pipeline to maintain.

**JevHarness** (github.com/TianyuCodings/JevHarness, by NanoJev's author): not a model — an **authoring + reflection loop**. An authoring LLM writes a task-specific harness (feature code, Jev `state`/`questions`/`criteria`, decision logic); the harness then runs frozen, without the authoring LLM, making its Jev calls per decision; optional GEPA reflection improves the harness against rewards using complete execution traces. Pokémon demo: eval win rate 25 % → 75 % over 5 reflection rounds; median full decision 568 ms, median individual Jev request 269 ms (independently corroborates hosted-Jev latency claims). Two implications here: (1) its reward-driven refinement needs a reliable reward — which is precisely what Stage 0 provides (recall@K / selection F1 as reward). Adopting JevHarness as the **authoring methodology** for the J1 reranker questions and J5 gate questions (instead of hand-writing instructions/criteria) is a natural Stage-3+ option, but only after the benchmark exists (no reward, no reflection). (2) Its freeze-the-harness philosophy — LLM authors during development, deterministic code + Jev executes in production — matches this repo's §15 determinism stance exactly: the reflection loop stays outside production, only the frozen artifact ships. Verdict: **methodology to adopt post-Stage-0; nothing to do now.** Hardware-independent by construction (reflection is dev-time; the frozen harness calls whichever decision-model provider it was authored against).

## 6. Recommended roadmap (benchmark-first; nothing selection-affecting flips default without numbers)

**Stage 0 — selection-quality benchmark (prerequisite, independently valuable).** The repo has NO golden query→expected-pattern set and no latency benchmark (no pytest-benchmark, no precision/recall harness; `tests/verification/test_perf_smoke.py` survives only as stale bytecode). Build `tests/benchmark/` (excluded from default runs): ~60-90 expert-reviewed scenarios across the 9 categories with 2-3 sibling-family variants each (catches category confusion), labels = expected primary + acceptable-supporting sets, **scenario-family split** so thresholds calibrated on train are tested on held-out families. Label production per user decision: LLM-drafted from the catalog (docs/design-patterns.md + each record's problem/use_cases), then user reviews/corrects once. Metrics: recall@K, acceptable-primary F1, supporting F1, veto/conflict violations, ECE/Brier (calibration), risk-coverage, stage and end-to-end p50/p95. This benchmark gates every selection-affecting change (Jev or open-source) AND unlocks the §5 succession: Laya/Von fine-tuning, NanoJev label synthesis, and JevHarness reflection (recall@K as reward) all consume it.

**Stage 1 — Jev reasoning gate (pure latency, provable now).** `JevClient` + config section (four surfaces: src/config.py field + effective_parameters key, config/config.json env placeholder, docker-compose passthrough, both guides §14) with shipped default **enabled=false** (requirement text would leave the machine — opt-in, not silent). Gate inside `ReasoningClient.run_pre_llm`; "no" → empty non-degraded trace (disabled-phase shape). Same PR: remove the discarded retry-phase reasoning block (pipeline.py:1625) and reconcile the mutation-scope drift (§8). Proof: live A/B (gate on vs off, same requests), degradation test (Jev unreachable → pipeline byte-identical decisions), property oracle + mutation ledger row + FizzBee reasoning_retry model updated for the control-flow change. Expected: on gated requests saves up to 19-21 sequential LLM calls + 19-21 subprocess spawns; on ungated requests costs ~0.1-0.5 s per phase.

**Stage 2 — Jev weights pilot (default-off).** Produce the raw 8-axis vector via 8 score questions in one call; map /3 → [0,1]; feed the existing `RequirementWeightsBatch` validation and ALL deterministic post-processing untouched (max-normalize, smoothing, E4 mean fallback stay — an all-zero vector hits the same E4 safety net, no special-casing). Gate: offline replay vs LLM weights on the Stage-0 set (primary-F1/overlap), then live A/B latency. Saves a 60-120 s call per request and removes the zero-vector second-batch risk statistically.

**Stage 3 — decision-model reranker (opt-in provider).** Implement `RerankerProtocol.rerank(query, documents, top_n) -> list[(index, score)]` best-first, with TEIReranker's shape guards (indices in range, deduped, sorted); per-doc noul p(yes) = score. One call for a ≤40-doc pool (~40k tokens: fits TypeSafe-direct 64k; chunk at 20 docs/call if ever routed via OpenRouter's 32k). The existing tail-rank repair (retriever.py:369-379) already tolerates partial responses. Gate: recall@K vs the cross-encoder on the Stage-0 set — the compact-capsule experiment (top-20 overlap 18/20 between compact and full evidence) shows deep ranking is insensitive to evidence detail, which supports feasibility but replaces nothing empirically. Provider ladder for this stage: hosted TypeSafe Jev first (quality lead, §5); a local `/v1/systemone` server (Kev 4B or Rizzo Flow) as the data-governance alternative at some quality cost; a fine-tuned Laya/Von reranker-scorer as the end-game once Stage-0 labels exist. On pass: recommend default flip; on fail: keep `tei`, costs one decision-model call when opted in. Tier note (§5): this stage's latency case is a Tier-A/C argument. On CC ≥ 7.5 GPU hosts, move TEI to CUDA FIRST (`make docker-build-tei-embed-gpu` as shipped, plus a matching CUDA rerank image) — if that meets the latency target, Stage 3 there is justified only by measured selection quality or provider cost, not seconds.

**Stage 4 — category router (conditional).** Only if Stage 2/3 quality holds. Soft narrowing with confidence floor (<0.5 → full corpus), never a hard router.

Projected end-to-end (Tier-A/CPU host — the 1162 s baseline is a CPU-tier measurement) if Stages 1-3 land and quality gates pass: 1162 s → roughly 400-650 s (−280-400 s rerank, −60-120 s weights, −150-250 s gated reasoning; remaining floor = A+B + G + H generative calls + query embeddings 13-29 s/part). On Tier-B GPU hosts the rerank term largely vanishes anyway once TEI runs on CUDA, so the same roadmap yields smaller gains concentrated in the hardware-invariant J4/J5 (LLM round trips). All projections require live A/B confirmation; vendor latency is a claim until measured (JevHarness's 269 ms median Jev request is independent corroboration, not proof for our states).

## 7. Governance, calibration, and cost

- **Data flow**: gating/weights/rerank questions send requirement text (and for J1, catalog excerpts) to the decision-model provider — TypeSafe by default, a local server if the §5 data-governance path is chosen. Default-off shipped config + loud startup health (`ok | unconfigured | error: …`, `fail_fast=false`, copying the reasoning-client contract: silent per-call degrade, `asyncio.CancelledError` re-raised, circuit breaker reuse from `src/provider_health.py`).
- **Pin + calibrate**: pin the hosted model (`jev-1.13.0`); log the resolved `model` from each response; per-question threshold constants (never shared across primitives); ECE/Brier on held-out families before trusting any threshold; risk-scaled confidence floors (0.5 escalate, higher for selection-adjacent uses). A self-hosted provider needs the same calibration pass on the same golden labels — an uncalibrated local model is not a drop-in.
- **Cost**: J1 ~40k input tokens/part ≈ $0.01-0.017/part ≈ $0.13/request at 8 parts; J4/J5 states are small (<2k tokens) → ≪ $0.01/request. Output free. Local providers trade that bill for GPU/CPU time on the box.
- **Degradation invariant**: a decision-model outage must never fail a tool call — Stage 1 returns the empty trace, Stage 2 falls back to the LLM weights call, Stage 3 falls back to the TEI provider.
